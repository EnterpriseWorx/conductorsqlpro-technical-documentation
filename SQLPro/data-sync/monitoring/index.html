Introduction

Sync Monitoring shows the health of your sync configurations and the status of individual tables.

To get started, open SQLSync from the landing page, then select Data Sync Sync Monitoring:

Sync Monitoring summary

The summary lists each sync configuration with hosts, databases, table list, last sync date, and status counts.

Issues only hides configurations that have no current issue. A configuration is an issue when it has table errors, checksum errors, or tables that count as behind. The choice is kept for the browser session. Use Refresh to reload the summary.

Key columns:

  • Sync Configuration Name
  • Source Host / Source Database
  • Target Host / Target Database
  • Table List Name
  • Last Sync Date
  • Total Tables
  • Pending/Resync
  • Syncing
  • Disabled
  • Errors
  • Checksum Errors - counts tables with row-count mismatch, checksum mismatch, or data movement during checksum. Does not include Ignored.
  • Behind - Change Tracking tables that are syncing, have no error message, and whose last check is older than the configuration schedule's minutes behind threshold. Destructive Load tables are excluded. Schedules with a threshold of 0 contribute no behind tables.

Click a count (for example Errors, Behind, or Total Tables) to open the detail page filtered to that configuration and status. Behind opens the detail page with Sync Status Behind.

Sync Monitoring details

The detail page lists tables for one or more configurations. Use the table column selector to show extra fields such as Source Row Count, Target Row Count, and Row Count Difference (those are hidden by default).

Key detail columns include:

  • Source Host / Target Host
  • Source Database / Schema / Table
  • Sync Type - Change Tracking or Destructive Load
  • Columns - All columns, or Subset (n) when column filtering is enabled
  • Last Delta Check
  • Status
  • Checksum
  • Error Message

Header actions:

  • Back to Sync Monitoring - return to the summary
  • Refresh - reload the detail list

Filters

  • Sync Configuration - limit to one configuration, or show all
  • Sync Status - Pending, Syncing, Disabled, Errors, or Behind
  • Checksum Status - Matches or Not Matches
  • Clear Filters - reset all filters

Behind lists syncing Change Tracking tables with no error message whose last check is older than the schedule threshold. It does not list Destructive Load tables.

Status meanings

Table sync statuses:

  • R - pending resync (marked by you or the system)
  • Q - resync enqueued
  • P - pending partial resync
  • M - partial resync enqueued
  • I - pending / in initial sync
  • S - syncing. Change Tracking tables receive deltas. Destructive Load tables wait for the next resync
  • D - pending disablement
  • E - disable enqueued
  • N - disabled / not syncing
  • X - error

UI status filters group these as:

  • Pending - I, R, Q, P, M
  • Syncing - S
  • Disabled - N, D, E
  • Errors - X

Checksum results may show:

  • Matches - source and target row counts and checksums match
  • RowCountMismatch / ChecksumMismatch - counts or checksums differ
  • DataMovement - source data changed during checksum verification
  • Ignored - checksum issue was acknowledged with Ignore Checksum Issue and will stay out of checksum error alerts until the next checksum run

Note

Checksums compare the synced columns for each table (the Table List subset plus primary keys when a subset is configured, otherwise all source columns). String columns are included using a short prefix and a binary collation. Date/time columns other than time are compared at second precision, and time is compared to millisecond precision. money and smallmoney are compared as decimal(19,4) and decimal(10,4) so SQL Server and Fabric agree. Binary, image, XML, and timestamp columns are excluded, as are sync metadata columns named C4SQL_*, because source and target platforms can compare them differently. MySQL tables compare row counts only.

Note

If delta or checksum work is skipped after Max delta/checksum retries, the table status is left unchanged and Error Message explains the skip (for example Delta sync skipped after N retries: … The table will be retried on the next delta sync.). The table is tried again on the next matching schedule run.

Bulk actions

Select one or more tables to enable bulk actions. Two menus appear:

  • Next Schedule Options - mark work for the next matching schedule run
  • On Demand Options - queue the same kind of work immediately

Next Schedule Options:

  • Mark Selected for Resync - marks tables for a full reload on the next resync schedule run
  • Mark Selected for Partial Resync - replays Change Tracking history within the retention window on the next resync schedule run (does not drop or reload the target table). Destructive Load tables are skipped
  • Disable Selected - stops syncing on the next delta schedule run

On Demand Options:

  • Run Delta for Selected - queues an immediate delta sync. Only tables with status Syncing are queued. Destructive Load tables are skipped
  • Calculate Checksum for Selected - triggers checksum calculation. This still runs for Destructive Load tables (the checksum schedule does not)
  • Ignore Checksum Issue - marks selected tables as checksum status Ignored. They no longer appear in checksum error alerts until the next checksum run recalculates them
  • Resync Selected - queues a full reload now for each selected table on an active sync configuration
  • Partial Resync Selected - queues a Change Tracking replay now. Destructive Load tables are skipped
  • Disable Selected - queues disable now for each selected table on an active sync configuration

MySQL checksums from either menu compare row counts only.

Confirm the change before the action runs.

Warning

A full resync drops and recreates the target table, then reloads all data for that table.

Tip

Use partial resync when checksum drift is likely still within Change Tracking retention (typically 7 days). It is faster than a full reload because the target table is left in place. If Change Tracking history has already expired, or checksum still fails after a partial resync, use a full resync instead.

Tip

Use Ignore Checksum Issue when you have investigated a mismatch and want to clear it from alerts temporarily. Run Calculate Checksum for Selected (or wait for the next checksum schedule) to re-evaluate the table.

Tip

If tables remain in pending status or show errors, check Queue Monitoring and confirm the related schedule is active.

Tip

Use Run Delta for Selected when you need Change Tracking applied now instead of waiting for the next delta schedule. Use Resync Selected, Partial Resync Selected, or Disable Selected under On Demand Options when that work should start now rather than on the next schedule.
